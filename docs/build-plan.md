# Body Inc. Construction Plan

Status: proposal for team review, 2026-10-23. This plan builds the architecture in `docs/architecture.md` on the schedule in design doc 14.2 (`docs/design-doc.md`). Owners follow design doc 15 and remain suggestions until the team confirms them. Every milestone ends in checks that can fail; a milestone is met only when its checks pass on `main` in CI, not when the work "looks done".

Also as of 2026-10-24 S4 is done. Content files are described by JSON Schema files in `content/schema/`, checked by a schema subset implemented in `core/content/schema.ts` rather than a library, so that core keeps no dependencies and problems come back as codes that `tools/check-content.ts` phrases in Chinese; a keyword outside the subset throws instead of being silently ignored, and a lint rejects any object schema that does not state `additionalProperties`, so no schema can let unknown fields through by omission. `tools/content/make-content-types.ts` writes `core/content/generated.ts`, which holds the schemas (core cannot import `content/`) and their TypeScript types; the tag and enemy loaders and the feedback table now take those types, so renaming a field in a schema fails compilation, which was confirmed by renaming `performance`. `check-content` maps every JSON file under `content/` to a schema, reports files that no schema claims, then runs the game's own loaders for references between files. `sim/params.js` now reads `content/params.json`, which keeps each parameter's DOC or ASSUME comment in a `notes` map that must name exactly the parameters in `defaults`; the outputs of `run.js`, `check.js`, `accept.js`, `ladder.js` and `discriminate.js` were byte-identical before and after the move, and changing one parameter changed the output, so the comparison could detect a difference. The schedule card schema follows content-spec section 1 without its department demand fields, which belong to the removed token model; it has fixtures but no real cards yet, and P1 should settle its fields. Loader messages for cross-file references are still English.

Also as of 2026-10-24 S10 is done. `view/text/wrap.ts` breaks lines by character with the rules of art direction 8.2 (closing punctuation never starts a line, opening punctuation never ends one, a no-break space keeps a number with its unit, a 〈〉 page name stays whole) and takes the width function as an argument, so Node tests run it with a fixed width model and the game with canvas `measureText`. Fifteen dialogue lines from the design doc and content-spec (`test/fixtures/text/dialogue-samples.json`; the repository has no separate dialogue style guide, so these stand in for one) fit 30 characters and 3 lines at 100% and 125% text size, both in the Node model and when measured in Chrome with Noto Sans TC, where the widest line came out at exactly the 660 px cap. The font gate in `view/text/fonts.ts` turned up two traps. First, Google Fonts serves Chinese in about a hundred unicode-range slices per face, and `document.fonts.load(font)` without text loads only the slice holding a space, so the gate loads the corpus of every character the game can show (printable ASCII, the line breaker's punctuation and all of `content/strings`). Second, Chrome's `document.fonts.check()` returned true for a character whose slice was never loaded, so the gate checks each slice's status itself. All game text goes through `addText`, which in development throws on text created before the gate or on a character outside the corpus; a test keeps other view files from creating Phaser text or writing Chinese literals, and the HUD labels moved to the string table. A warm cache let a build without the gate pass by winning the race, so the dev-only `?fontDelay=<ms>` parameter simulates a slow cold load; with it, the build without the gate threw at the first HUD label, the build that loaded fonts without the corpus stopped at Boot listing the missing characters, and the real build started cleanly after the delay. Fonts still come from Google Fonts; self-hosted subset woff2 and the missing-glyph check belong to the art pipeline (art direction 8.2), and the dialogue box padding (32 px a side) is an assumption until the box is built. S11 adds the save skeleton. `core/save/save.ts` decodes a slot stored as `{ schema, data }`: an older version runs `migrations[v]` step by step and is then checked against the slot schema with the S4 validator, a newer version is refused so a save from a newer build in another tab is never overwritten, and unreadable text or a payload that fails the schema falls back to the defaults. `checkSlotDef` fails the tests when a slot version is raised without a migration for every step. `app/storage.ts` wraps `localStorage` under the `hbc.v1.*` keys of ux-spec section 8 and turns every failure (storage unavailable, read refused, write blocked or over quota) into an issue instead of an exception; corrupt text is copied to the per-slot key `hbc.v1.corrupt.<slot>` before defaults replace it (ux-spec section 8 was changed from a single shared key, which let one corruption erase another backup). A slot is locked against writes whenever its stored text was not safely read or kept aside: a newer version, a failed read, or corrupt text whose backup failed. Boot loads the settings slot (text scale and game speed) and writes it back when it was empty, migrated or replaced, and the HUD shows each distinct issue as a notice from the string table. Nothing consumes the loaded settings yet: the registry holds them and the `SaveStore` for the settings screen and the text-scale and game-speed systems, which do not exist yet, so neither setting has any effect in this build. A normal browser never fails a write, so the dev-only `?storage=blocked` and `?storage=full` parameters make writes throw; with `?storage=blocked` the game started with the notice on screen, a planted `{broken` save was backed up and replaced, and a clean reload showed no notice. Cross-run progress, the semester run and story progress get their own slots when those systems exist. P2 adds variant selection at room entry. `core/rooms/entry.ts` turns a parsed room into an `EnteredRoom` from the tags at the moment of entry: objects of variants whose `when` fails are dropped, and a Spawn whose own `when` fails is dropped too, while the `when` of other kinds is left to the system that owns it. `createGame` accepts only an `EnteredRoom`, so a caller that forgets the tags fails typecheck instead of silently getting the base room. Decoration props follow art direction 7.3: tile objects in a `props` object layer (also inside a variant group) that point at an image-collection tileset over `public/assets/props/`, read by `core/rooms/props.ts` for both the map check and the view, and drawn from the scene atlas frame of the same name; Boot checks every prop of every variant against the atlases, so a missing frame stops Boot even when no one has entered with the right tags. The greybox brain corridor (`tools/maps/make-brain-corridor.ts`) has one clock vent with its adenosine, and `variant:sleep_debt_2` adds two vents with one adenosine each; it lives in the greybox folder because the brain chapter would need its own tutorial room and bed, which are P7 content. Until P1 produces tags, dev builds take the room and tags from the URL (`?room=greybox/brain-corridor&tags=sleep_debt:2`). Tests pin one vent and one adenosine at `sleep_debt` 0, 1 and 1.9 and three of each at 2 and 5. Headless Chrome screenshots show the same: the page with no tags is byte-identical to `sleep_debt:1`, and `sleep_debt:2` shows the two extra vents. Tile layers inside variants are not drawn yet and the map check rejects them, and `make-greybox.ts` now shares `tools/maps/room-kit.ts` with the corridor script, with the greybox room regenerated byte-identical.

Also as of 2026-10-24 P3 is done. The rejection gauge (design doc 5.4) lives on the operator and charges 0.8 per staple that hits a defeatable enemy or disperses a reforming one and 10 per perfect dodge, each times the chairman's spirit P; a staple that bounces off an immune enemy is not a hit and charges nothing. Other stationery (+1.5) and folder parries (+15) are left for the packages that add those tools. P comes from `core/spirit.ts`, which applies the glossary formulas S = max(0.3, 1 - 0.07 x sleep debt) and P = 0.5 + 0.5 x S with the coefficients of `content/params.json`, and is fixed at room entry like the variant layers. Charge is rounded to six decimals so that 125 rested hits fill the gauge to exactly 100. The stamp (R or the middle button) needs a full gauge, empties it on the press, keeps the operator still and invincible for the 21-tick startup and lands on the 22nd tick, covering every hittable enemy whose feet are within 3.5 tiles of the operator's. Defeatable enemies lose 25 and freeze for 10 ticks; on reforming and immune enemies the stamp is void, which leaves them unchanged and shows the grey "查無可駁回事項" note with a line per solution. The 40-point boss damage and cancelling a proposal belong to P4. Clinging is a flag in `content/enemies.json` that only reforming enemies may carry; adenosine has it. A clinging enemy drifts toward an operator within 5 tiles at 1 tile per second (both placeholders the design doc does not fix) and latches on at contact, at most one per tick and never through invincibility, so dodging through a crowd still works. Each stack slows by 5% through the existing 15% cap, and the third stack is a forced nap: the rule clock, which game state now carries, advances one hour, the stacks go back to their spawn points as dispersed and reform there six seconds later, so the nap clears the stacks without removing any adenosine. A forced leave keeps both the stacks and the gauge. The exam-fight rule, where three stacks fail the current question, waits for the exam fight. Because the automated Chrome session ran the game at 2 frames per second, the browser check drove headless Chrome over the DevTools protocol at 61 frames per second with real key events: the stamp emptied the gauge, closed a salesman and showed the void note on an alcohol barrel; three adenosine stacks advanced the HUD clock from 08:00 to 09:00 and sent all three back to their vents. ## 1. Principles for the build

The build proceeds from the boundary outward. The first week produces the empty skeleton with its guard rails (boundary check, content schema, map check, CI, deploy) before any feature, because retrofitting a boundary after features exist is the expensive direction. Features are then built as vertical slices: each one lands its core rules with Node tests, its adapter, and its view in the same pull request, so the boundary is exercised by every feature instead of being designed once and ignored.

Placeholder art is used from day one. The placeholder atlases generated from `public/assets/manifest.json` already follow the visual semantics of art direction 13.5 (badge for defeatable, dashed purple for reforming, grey hatching for immune), so the 11/8 alpha can test whether new players read the badge rule before the final sprites exist. Real art replaces placeholders by overwriting files; no code change is expected or allowed for an art swap.

## 7. Rules for every pull request

A pull request is mergeable when `npm run typecheck`, `npm run test`, and `npm run check` pass, the change keeps rules in core and presentation in view (the boundary check enforces the mechanical part, review enforces the rest), new rules have Node tests, and new checks come with a fixture that proves they can fail. Content-only pull requests from non-programmers need only the schema and map checks. Each module owner in architecture 10 reviews changes to their module.

## 8. Risks specific to the build

**The boundary slows the first week.** Writing commands, events, and selectors before the first sprite moves is slower than putting logic in a scene. The payoff is that combat feel can be tuned by numbers in core tests and that the simulation and the game share one model; the cost is bounded to S3 and S7.

**Core collision takes longer than a week.** Writing collision in core (architecture 5) adds about a week to the first two weeks and lands on the combat owner during the feel prototype. S8b is therefore paired work and kept deliberately small (no slopes, no rotation, no continuous collision beyond per-axis stepping). If S8b is not passing by 10/29, the dodge distance is split into sub-steps no longer than half a tile per tick rather than adding a general solver.

**TypeScript slows the non-programmers.** Content authors never touch `.ts` files: dialogue is CSV, rooms are Tiled maps, data is JSON validated by schema, so the language choice affects only the four programmers.

**The old simulation diverges from the game.** Until L3, `sim/` still runs the old model. It must not be used to justify new numbers after S4; balance decisions after 11/1 use the shared core only.
