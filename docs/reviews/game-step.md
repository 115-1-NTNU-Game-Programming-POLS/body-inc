# `step()` 結構審查（issue #75，第一階段）

審查對象是 `src/core/game.ts` 的 `step`。它負責把一個房間的戰鬥往前推一個規則幀。這份文件是 #75 第一階段的交付物：說明 `step` 目前分成哪幾段、各段之間的順序限制，提出重構方案，並列出路上發現的問題。這個階段**沒有改 `src/` 的任何東西**。

審查基準：`main` 的 8254ff8（2026-11-10）。issue 開立時 `step` 是第 703 至 1265 行，共 563 行；之後各章節又加了東西，現在是第 854 至 1546 行，共 **693 行**，整個檔案 1742 行。下文的行號都以 8254ff8 為準。

## 1. 特性測試（characterization tests）

`test/core/step-characterization.test.ts` 與 `test/core/step-characterization.json`。

**做法。** 每個情境先透過章節層開一間房（`startChapter`，必要時用 `stepChapter` 走到前置狀態，例如躺上床、坐進考場），之後**只呼叫 `step`**，由一個帶種子的腳本玩家逐幀給輸入。每一幀把 `[前一個鏈值, stateHash(狀態), stateHash(事件)]` 再雜湊成新的鏈值，每 30 幀和最後一幀記一次，存進 JSON。重構後只要任何一幀的狀態或事件有一點不同，該情境從那個 30 幀區間開始的鏈值就全部不同，測試會指出最先分歧的幀數區間。

**腳本玩家**（`bot`）每 45 幀換一次計畫：走向最近的敵人、後退、繞圈、往隨機方向走、站著不動，或走向房裡某個物件（門、拉桿、箱子、床）。它會一陣一陣地按住射擊，隨機閃身；附近有敵人預備出招時閃身機率會提高；量表滿了會蓋章，偶爾換文具、叫夥伴、按互動鍵。它用的是測試自己的 LCG 亂數，不會動到遊戲本身的 RNG。這是為了讓狀態空間被廣泛走過，不代表任何規則。

**情境**，共 36 個（最初 33 個，#110 合併後補上胃章 Boss 的 3 個）：

- **一般遊玩**：灰盒房間、大腦章教學、開放辦公室、兩個咖啡因 Boss 房、肝臟頂樓的敬酒 Boss、派對的乾杯小弟、肝臟工廠、巡邏核心與巡邏服務台（福利卡全開）、輔助全開的巡邏倉庫、序章倉庫、卸貨區、胃章三個實驗室、期中考場、序章會議室。
- **針對性**：
  - 一次蓋章蓋到六種不同類別的敵人
  - 咖啡因 Boss 的提案被蓋章駁回，一路打到第二階段與斷電
  - 站在腺苷中間直到強制打盹
  - 完整咖啡因斗篷下穿過腺苷
  - 腺苷飄進休息區的圍欄
  - 公文夾連段打經理的盾
  - 胃酸溶解塊狀物
  - 睡在夜間實驗室直到被吵醒
  - 乙醛霧
  - 用公文夾格擋推銷員、傳單手、能量飲料推銷員和乾杯小弟，福利卡全開
  - 兩個 Boss 在攻擊還在空中時被收尾
  - 量表全滿時在訂單和酒桶旁蓋章
  - 胃章 Boss（報復性宵夜部長，`stomach/boss-arena`）：腳本玩家站到箱子的飛行路線上舉公文夾，走到退件、格擋、兩個階段、胃抗議和結案；另一個情境放著他不管、只用釘書針打（彈開和胃抗議）；第三個從第二階段開始（加大份）。這需要腳本玩家多一種打法 `guardDeliveries`，只在這三個情境開啟，不影響其他情境。三個突變（退件傷害改用公文夾自己的、胃抗議的範圍從第 0 幀起算、胃抗議不發預警）都會讓其中兩個情境失敗。

**什麼時候可以重新產生 JSON。** 只有規則**刻意**改變時才可以（例如調了數值），執行 `UPDATE_STEP_CHARACTERIZATION=1 npx vitest run test/core/step-characterization.test.ts`，並在 PR 裡說明哪些情境變了、為什麼。重構的 PR **永遠不能**重新產生它。另外，這份測試會讓**其他人**調數值或改敵人行為的 PR 也必須重新產生 JSON，這是刻意的：那也是 `step` 的輸出變了。**改了情境用到的地圖也一樣**：#110 在夜間實驗室加了一道門，夜間實驗室的 4 個情境就從第 1 幀起分歧，而規則本身沒有影響任何既有情境（把地圖換回原版，33 個全部通過）。這點需要在團隊內說清楚，見第 7 節的問題 Q1（決定：保留到第二階段結束）。

重新產生時要跑整個檔案：寫入只在所有情境都跑完時發生，用 `-t` 只跑一部分時什麼都不會寫，也不會提示。

## 3. 順序限制

下表列出不能隨意對調的順序。「證據」欄寫的是程式裡的註解，或第 1 節的突變結果。

| 限制 | 理由 | 證據 |
| --- | --- | --- |
| P5 → P6：先由輸送帶帶動營運長，再判定推箱 | 推箱看的是營運長移動後的位置 | 突變「輸送帶在箱子之後」失敗 |
| P6 → P7 → P8：箱子、開關、門 | 壓板上的箱子、港口收到的箱子會改變開關；本幀打開的門要能立刻通過 | 註解 930–933；突變「門用上一幀的開關」失敗 |
| P8 在 P15d 之前：門的判定用的是**被釘書針釘之前**的開關 | 刻意的：被釘書針打開的拉桿下一幀才算「新打開」，好讓貼著門的營運長能通過 | 註解 1512–1513 |
| P10 → P11：敵人全部行動完，訂單才落地 | 上限與目標格要看大家移動後的位置 | 註解 1059–1062 |
| P10 → P12：舊的範圍攻擊先老化，新的才加入 | 新範圍攻擊的第一幀是第 1 幀 | 註解 997；突變「從第 0 幀起算」失敗 |
| P10 → P13 → P15：圍欄在敵人移動之後、武器之前 | 飄進圍欄的那一幀就關住，不會再被打散 | 突變「圍欄也關黏著的」失敗（屬於規則，不算順序，但同在這一段） |
| P15 → P16 → P17：武器先打、再收回已結案 Boss 的攻擊、最後營運長受擊 | 被打倒的 Boss 不能在同一幀還打到人 | 註解 1286–1287；兩個 Boss 收尾的突變失敗 |
| P15d 拉桿要在撞牆之前判定 | 拉桿常裝在牆上 | 註解 1248–1252；突變失敗 |
| P17 內部：近戰 → 子彈 → 範圍，各自依 id 排序；一幀最多受擊一次 | 結果不依賴陣列順序 | 註解 1292–1293；但「範圍先於近戰」的突變沒抓到（第 6 節） |
| P17b 反彈的子彈加進 P15d 的 `flying` | 反彈的子彈下一幀才開始飛 | 讀程式得知 |
| P17 → P19：先受擊，後黏身 | 受擊後的無敵讓同一幀不會再被黏住 | 突變「黏身先於受擊」失敗 |
| P17、P19 → P21：睡眠在所有「打到營運長」的事件之後 | `struck` 讀的是本幀已經累積的事件 | 第 1501 行 |
| P22 → P23 → P24 | 考試讀本幀所有事件；強制離場要排除房間事件 | 註解 1526、1537–1540 |
| `byId()` 的快取 | 依賴「同一幀內敵人只增不減」，所以排序後的 id 只會隨數量改變 | 註解 1087；P10 之後才第一次呼叫 |

**不受順序影響的部分**（可以各自獨立，搬動也不會改變輸出）：P2、P4、P9 互相獨立；P15a 與 P15d 在目前的數值下實際上可以互換：蓋章起手時營運長不能射擊，而前幾幀射出的釘書針會在蓋章落下之前就命中或消失。突變也顯示兩者互換時輸出不變，但這不是程式結構保證的，見第 6 節。

**最難拆的地方。** P15 和 P17 用**閉包**共用狀態：`hitEnemy` 會改 `op`（充能）、`bind`、`enemies`，還會呼叫 `bindHit` 與 `splash`；`absorb` 會改 `op` 和 `freeze`，`caught` 讀 `op.action`。這些閉包被 P15a 到 P15d、P17a 到 P17c 共用，所以如果把各階段拆成純函式、各自傳入傳出，這幾個值就要在每個函式之間來回傳遞。

## 4. 重構方案

### 考慮過的選項

**A. 每個階段一個純函式，輸入輸出都收窄**（issue 提到的明顯做法）。
- 好處：每個函式讀寫什麼都寫在型別上。
- 問題：P15 與 P17 的閉包共用 `op`、`enemies`、`bind`、`boostUntil`、`freeze`、`events`、`nextId`，所以每個函式的參數和回傳值都會是六、七個欄位的物件，呼叫端還要逐一接回來，比現在更容易漏傳。現在的 `let` 至少讓「最新的 `op`」只有一份。

**B. 明確的有序階段清單，作用在一個「本幀工作區」物件上。**
- 做法：定義 `interface Tick`，欄位對應現在的那些 `let`（`op`、`enemies`、`boxes`、`grid`、`switches`、`zones`、`shots`、`projectiles`、`flying`、`nextId`、`rng`、`bind`、`boostUntil`、`freeze`、`events` 等）。每個階段是 `(t: Tick) => void`，放在 `src/core/tick/` 下依主題分檔。`step` 本身變成約 40 行：建立 `Tick`，依序呼叫各階段，每一行旁邊用一句註解寫出它必須排在這裡的理由（就是第 3 節的表）。
- 好處：順序本身變成看得見的一張清單；共用的閉包變成接收 `Tick` 的一般函式；每個檔案只放一類規則（例如 `weapons.ts` 放 P15 與 `hitEnemy` 一家），之後要加的螢光筆、修正帶就是加一個檔案、在清單上插一行。
- 代價：`Tick` 是可變物件。但 `step` 內部現在就已經是可變的（大量 `let`、`Map.set`），對外仍然只回傳新的 `GameState`，不可變的契約不變。另外，調換順序只要改一行，看起來太容易；但第 1 節的特性測試正是用來擋這件事的。

**C. 把 `GameState` 切成幾個切片，每個階段只拿得到自己的切片。**
- 好處最大：型別直接保證一個階段改不到別人的狀態。
- 問題：`GameState` 被章節層、畫面層、存檔、選擇器（`select*`）大量使用，切開要動到這些不屬於 #75 範圍、也不屬於我負責的檔案（`chapter.ts` 等）。而且第 3 節顯示，幾乎每個階段都讀寫 `op` 和 `enemies`，切片之間仍會大量重疊。

### 建議：B

理由：它讓第 3 節的限制在程式裡一目了然，又不會像 A 那樣產生又寬又容易漏接的參數，也不必像 C 那樣動到範圍外的檔案。每個階段的函式在檔案開頭用註解寫出它讀寫 `Tick` 的哪些欄位（就是第 2 節那張表的一列），讓 code review 時能檢查。

### 第二階段的步驟

每一步一個 PR，特性測試的 JSON 一律不動，並且必須通過：

1. 引入 `Tick` 型別與建立它的函式，把 P22 到 P24（組回狀態、考試、強制離場）搬成 `settle(t)`。從尾端開始，是因為它讀所有欄位，最先定義好 `Tick` 的全貌。
2. 搬出房間機關 P5 到 P8，放在 `tick/room.ts`。
3. 搬出敵人 P9 到 P14，放在 `tick/enemies.ts`。
4. 搬出武器 P15 與它的輔助函式，放在 `tick/weapons.ts`。
5. 搬出營運長受擊 P16 到 P17，放在 `tick/hits.ts`。
6. 搬出 P18 到 P21，放在 `tick/aftermath.ts`。
7. `step` 只剩階段清單。P0 到 P4 留在 `step` 開頭，或併成 `tick/operator.ts`。

完成後 `step` 約 40 行，最長的階段檔案（武器）約 200 行。
