# 房間、對話與卡片製作說明

這份說明給用 Tiled 做房間、用試算表寫對話的組員。程式不需要改動：房間是 `public/assets/maps/` 下的 Tiled 檔，章節的房間怎麼接在一起寫在 `content/chapters/` 的一個 JSON 檔，對話寫在 `content/dialogue/` 的 CSV 檔。每一種檔案都有檢查腳本，錯誤會用中文指出檔名與位置。設計依據是設計文件第 13.2 與 13.3 節；說明與設計文件不一致時，以設計文件為準。

## 做一間房

先安裝 [Tiled](https://www.mapeditor.org/)，再用它開啟專案根目錄的 `body-inc.tiled-project`。物件類別（Door、NPC、Bed 等）與地圖屬性會以下拉選單或勾選框出現，不必背屬性名稱。

新房間從範本複製。`public/assets/maps/_template/` 有四份範本，依房間所屬的世界挑選：`room-lobby.tmj`（大廳）、`room-warehouse.tmj`（肝醣倉庫）、`room-brain.tmj`（大腦）、`room-liver.tmj`（肝）。把檔案複製到 `public/assets/maps/<章>/` 並改名，章是資料夾名稱，房間名稱只用小寫英文、數字與連字號，例如 `public/assets/maps/brain/coffee-room.tmj`。範本是標準的 20 × 12 格房間，南牆已開一個 2 格寬的門，並放了玩家出生點（PlayerStart）。範本刻意沒有填 `organ`、`role`、`estSeconds` 三個地圖屬性，沒填就交出去，地圖檢查會失敗。目前只有 1 × 1 的範本；2 × 1 與 2 × 2 的大房間尚未提供範本，需要時請找程式組。

地圖屬性填這幾項：`organ` 是房間所屬的器官，`role` 是房間的用途（combat、puzzle、rest、treasure、transit、core），`estSeconds` 是預估通關秒數，`difficulty` 為 1 到 3。有敵人是「打不掉」的類型時，教學房要在 `tutorialFor` 填那種敵人的 id，詳見設計文件 5.5 節與 13.3 節。

房間畫在兩個圖塊圖層上。`floor` 圖層是地板，只負責好看。`walls` 圖層的每一個非空格都是牆，營運長走不過去，所以地板上的家具不要畫在 `walls` 上，除非它真的要擋路。場景裝飾的做法見 README 的「編輯地圖」。

## 房間裡的物件

物件放在名為 `objects` 的物件圖層。從 Tiled 的類別下拉選單選類別後，只填需要的屬性。下表列出目前有效果的類別；Hazard 目前只檢查格式，放進去不會有任何動作，要等負責的功能完成。

| 類別 | 做什麼 | 要填的屬性 |
| --- | --- | --- |
| PlayerStart | 營運長出生與強制下班（還沒打過卡時）回來的位置，每間房一個 | 無 |
| Spawn | 敵人生成點 | `enemyType` 從下拉選單選；`count` 數量；`respawnSeconds` 擊退後幾秒再出現，0 表示不再出現；`when` 條件式 |
| NPC | 可對話的角色，走近按 E 或 Enter | `npcId`、`dialogueId`（必須存在於對話 CSV）；`npcId` 與 `public/assets/manifest.json` 裡某個角色圖的名稱相同時（例如 `liver`），會自動畫出那個角色，否則畫一個佔位的人形 |
| Trigger | 營運長踩上去就觸發 | `event` 見下段；`eventId`；`once` 預設只觸發一次；`when` 條件式 |
| Door | 房間的門 | `socket` 朝哪個方向；`lock` 鎖的種類與 `lockParam`，見下方「門鎖與開關」；**物件的 Name 欄必填** |
| Switch | 開關（拉桿）或壓力板，用來開 `lock` 為 `switch` 的門，或啟動輸送帶 | `target` 選要開的門或輸送帶；`mode` 是 `toggle`（拉桿）或 `hold`（壓力板） |
| Box | 推得動的箱子，佔一整格，見下方「推箱與輸送帶」 | `boxType` 只決定外觀（`crate`、`glucose`、`acetaldehyde`、`food`）；`when` 條件式 |
| Conveyor | 輸送帶，把上面的箱子與營運長往一個方向送，見下方「推箱與輸送帶」 | `direction` 方向（N、S、E、W）；`speed` 是 `slow`、`normal` 或 `fast`；**必須畫成矩形** |
| Port | 調度口，收下送進來的箱子，收滿就打開一扇門，見下方「調度口」 | `need` 要收幾個箱子；`target` 選收滿時要開的門；`dialogueId` 收滿時開啟的對話，可留空；**必須畫成矩形**，每間房最多一個 |
| Bed | 床 | `bedType` 是 `nap` 或 `sleep`；`requires` 條件式，成立才能用；`unlocks` 是午睡沙發第一次用時順便解鎖的手冊頁代號，可留空 |
| Pickup | 撿得起來的道具，走近按 E 或 Enter | `itemType` 道具種類；`itemId` 見下方「道具與員工手冊」；`when` 條件式 |

Trigger 的 `event` 有七種。`checkpoint` 是打卡機：營運長踩上去時存檔、補滿心，之後強制下班會回到這裡，每次踩上去都算，不受 `once` 影響。`clock_advance` 讓章內時鐘前進，`eventId` 填分鐘數，必須是 1 到 4 位數的整數，例如 `20`；留空、寫小數、`1e1` 或文字都會被地圖檢查擋下。`dialogue` 開啟對話，`eventId` 填對話 id。`card` 翻開一張事件卡，`eventId` 填這一章卡組裡事件卡的 id，寫法見下方「卡片」一節。`rescue` 開啟一段急救，`eventId` 填 `content/rescue.json` 裡的 id，見「肝臟工廠與急救」一節。`cutscene` 會通知外層的過場，那個功能完成前沒有反應。`end` 結束這一章，`eventId` 留空，效果與 `sleep` 床相同，用在不以睡覺收尾的章節，例如序章下班打卡；它的 `when` 會被完成檢查當成「床的條件」來看，所以章節裡至少要有一張 `sleep` 床或一個 `end` 觸發點。

Bed 的 `nap` 是午睡沙發：時鐘前進 20 分鐘，黏在身上的腺苷全部回到原處，每張床只能用一次。午睡沙發的 `unlocks` 填一個存在於 `content/handbook.json` 的頁面代號，第一次躺下時解鎖那一頁，之後再躺不會重複；大腦章的沙發給〈短暫午睡〉，地圖檢查會確認代號存在；就寢門不看這個欄位。`sleep` 是就寢門：條件成立就結束這一章；章節檔有 `next` 或卡組有章末卡時接著翻章末卡、進下一章，否則回到標題畫面。`requires` 寫成條件式，例如 `caffeine<15`，不成立時床會回應「還睡不著」。條件式只能用 `content/tags.json` 裡的標籤，語法是標籤名、比較運算、驚嘆號否定、逗號表示「且」。

NPC、Bed、Trigger、Pickup 可以畫成矩形，也可以只放一個點。放點的時候，遊戲以 1 格大小、置中在那個點上處理。門一定要畫成矩形。

Door 的 `socket` 位置是固定的，檢查腳本會逐一指出放錯的地方：北門在北牆第 9 至 10 欄，南門在南牆（最後一列）第 9 至 10 欄，西門在西牆第 6 至 7 列，東門在東牆第 6 至 7 列。

## 門鎖與開關

設計文件 13.3 節規定房間裡的解謎必須自給自足，跨房間的進度只能靠全域狀態（時鐘、標籤）傳遞，門鎖的規則依此訂定。`lock` 有五種：

| `lock` | 什麼時候打得開 | `lockParam` 填什麼 |
| --- | --- | --- |
| `none` | 一直開著 | 留空 |
| `switch` | 同一間房裡每一個 `target` 指向這扇門的開關都打開時 | 留空 |
| `clock` | 章內時鐘落在開放時段內時 | 時段，例如 `08:00-10:00`；過午夜寫成 `22:00-02:00`，開到午夜寫成 `17:00-24:00`；開始的那一分鐘算在內，結束的那一分鐘不算 |
| `resource` | 條件式成立時，例如咖啡因殘留低於 50 | 條件式，例如 `caffeine<50`，語法與 `when` 相同 |
| `key` | 同一間房裡 `itemId` 等於 `lockParam` 的道具被撿起後；`lockParam` 留空的門永遠不開，用來封住不用的門口 | 鑰匙道具的 `itemId`，例如 `archive-key`；或留空 |

鎖上的門會掛一塊墨藍色鎖牌，圖示分別是鑰匙、拉桿、時鐘與量表，門打開時鎖牌消失；營運長碰到鎖著的門時，會依鎖的種類跳出不同的提示。時鐘與條件式每一刻都重新判斷，所以 `clock` 與 `resource` 的門會隨時間或標籤改變而開關。營運長貼著一扇鎖著的門等待時，門一打開就會直接走過去，不必退開再走一次。

Switch 有兩種。`toggle` 是拉桿：走近按 E 或 Enter 可以來回切換；用釘書機射中也會把它打開，但射擊不會把它關上，避免按住連射時開關一直跳動。拉桿可以放在牆面上，例如北門旁邊的牆面，釘書針會先打到拉桿才被牆擋下。拉起的拉桿會一直維持，離開房間再回來、強制下班回到打卡機都一樣，打卡時也會一起存檔，因為解開的機關就保持解開。`hold` 是壓力板：營運長站在上面，或有箱子停在上面時才算開，兩者都離開就恢復。壓力板本身不會被記住，但停在上面的箱子會，見下方「推箱與輸送帶」。一扇門可以有好幾個開關指向它，必須全部打開門才開。開關只能指向 `lock` 為 `switch` 的門或輸送帶，`lock` 為 `switch` 的門也至少要有一個開關指向它，否則地圖檢查會指出。放在 `variant:` 圖層裡的開關只在那個變體出現時存在，變體沒出現時，只靠它開的門就打不開。

要注意，營運長無法一邊站在壓力板上、一邊走進遠處的門，所以只靠壓力板開的門，要房間裡有箱子可以壓住壓力板才走得過去；地圖檢查判斷房間能不能走到時，只把放在 `objects` 圖層、`when` 留空的箱子算進去。灰盒章節的 `greybox/greybox-room` 北門與 `greybox/lock-hall` 示範了拉桿、時段與條件式三種鎖，可以用 `?room=greybox/lock-hall&tags=caffeine:100` 看到條件式的門關上；`greybox/archive` 的西門示範鑰匙鎖。

`key` 鎖的鑰匙一定要和門在同一間房，這也是設計文件「解謎自給自足」的要求。鑰匙可以是任何種類的道具，建議用 `file`（一份文件），因為它沒有別的效果。鑰匙必須放在 `objects` 圖層、`when` 留空：放在變體圖層或加了條件，換一組狀態再進房時鑰匙會不見，已經打開的門又會鎖上，所以地圖檢查會擋下。`lockParam` 寫了名字卻找不到同名道具，地圖檢查也會指出。鑰匙撿起來之後門就保持打開，離開再回來也一樣。

## 推箱與輸送帶

Box 是推得動的箱子，佔一整格，可以畫成矩形或只放一個點，遊戲取它中心所在的那一格。營運長正面貼著箱子，只按一個方向鍵持續推約六分之一秒，箱子就往那個方向滑一格；一直按著會一格接一格推下去。斜著按、同時貼著兩個箱子、正在閃身、受傷硬直或蓋駁回印章時都推不動。箱子不能推進牆、另一個箱子、門、NPC、床、道具、觸發區所在的格子，也不會壓到營運長、敵人或敵人出現的位置（敵人重生、重組、強制下班後都會回到那裡）。箱子對營運長、敵人與釘書針都是實心的。設計文件 13.3 節的物件類別沒有箱子，這是為了第二章的葡萄糖箱與肝臟章的乙醛箱新增的類別。

箱子停在壓力板上時，壓力板就算踩下，滑過去的途中不算。這是讓營運長離開壓力板、走進遠處的門的方法，灰盒章節的 `greybox/loading-dock`（從儲藏室東門或大廳東門進去）示範了整套流程：把板條箱往西推上輸送帶，拉起牆上的拉桿，輸送帶把箱子送到壓力板上，西門打開。

Conveyor 是輸送帶，佔它矩形範圍內的格子（以格子中心是否在矩形內判斷）。沒有任何開關指向它時一直運轉；有開關指向時，要每一個開關都打開才運轉，停下時箭頭變暗。運轉中的輸送帶每隔一段時間把停在上面的箱子往 `direction` 送一格：`slow` 兩秒、`normal` 一秒、`fast` 半秒，前方擋住時就等著，前一個箱子還沒完全離開的格子也算擋住，所以一排箱子在輸送帶上會隔一格前進；送到輸送帶盡頭的下一格後箱子停下。被輸送帶運送中的箱子，在抵達之前原本那一格也算實心，營運長不會走進去。營運長腳下那一格在運轉中的輸送帶上時，會以同樣的速度被帶著走。平常可以逆著走，只是比較慢；但按住射擊或身上黏著腺苷而變慢時，`fast` 輸送帶會比營運長走得快，逆著走反而會被往後帶，可以當作關卡的難點來用。輸送帶不會帶動敵人。

箱子的位置會記住，規則是「解開的機關保持解開」：離開房間再回來、強制下班或讀取打卡點時，停在壓力板上的箱子留在原地，其餘箱子回到地圖上的位置。所以把箱子推進牆角卡住時，出房間再進來就能重來。強制下班和拉起的拉桿一樣，不會把已經壓在壓力板上的箱子退回去。打卡也會存下箱子的位置，讀取打卡點時照同樣的規則擺回。箱子要擺回的位置剛好被營運長或另一個箱子佔住時，會改放到最近的空地板上，但不會放在調度口上，否則箱子沒被推就被收下。`when` 在進房時判斷一次，不成立時這一趟箱子不在房間裡。

地圖檢查會指出箱子放在牆上、兩個箱子放在同一格、箱子壓在門／NPC／床／道具／觸發區／調度口上、箱子壓到出生點、從門進房時營運長站的位置或 Spawn 敵人出現的位置，以及輸送帶畫成點而不是矩形。兩個物件的條件不可能同時成立時，例如一個箱子的 `when` 是 `breakfast`、另一個是 `!breakfast`，它們永遠不會在同一趟出現，所以放在同一格不算衝突；判斷看的是箱子、道具與 Spawn 自己的 `when`，以及所在變體圖層的 `when`。觸發區的 `when` 只決定它會不會觸發，觸發區本身一直都在，所以仍然算衝突。

箱子可以壓在拉桿上。這時釘書針會被箱子擋下，打不到下面的拉桿，要先把箱子推開。

## 調度口

Port 是調度口，序章倉庫用它收葡萄糖箱。箱子停在調度口的任何一格上時就被收下，從房間消失；推動時滑過的途中不算，要停下來才算。輸送帶每送一格箱子都會停一下，所以輸送帶帶著箱子經過調度口時，箱子會被收下。收下的箱子會記住，離開房間、強制下班或讀取打卡點都不會吐回來，和拉起的拉桿一樣。調度口上會顯示「已收／`need`」，收滿時變成藍色，`target` 指的門打開，`dialogueId` 有填的話接著開啟那段對話，對話裡可以寫收滿之後的效果，例如補血糖或解鎖手冊頁。這段對話只開一次；收滿的那一刻營運長剛好倒下時，對話會在回到打卡點之後、下一次待在調度口所在的房間時開啟，不會就此消失。

調度口在門鎖的規則裡就是一個開關，收滿時打開，所以 `target` 和 Switch 一樣，只能指向 `lock` 為 `switch` 的門或輸送帶；同一扇門如果還有拉桿或壓力板指向它，要全部成立門才開。章節檢查把調度口指向的門算成通路，因為 `need` 已經保證房間裡的箱子夠用。調度口必須畫成矩形，每間房最多一個；第二個調度口會被地圖檢查指出。調度口佔哪些格子和輸送帶一樣以格子中心為準，所以矩形至少要蓋住一格的中心，其中至少一格是地板；太小而蓋不到任何格子中心（`port-shape`），或蓋住的格子全是牆（`port-wall`），箱子都停不上去，地圖檢查會指出。`need` 至少是 1，而且不能多於房間裡放在 `objects` 圖層、`when` 留空的箱子數，否則房間永遠無法收滿，地圖檢查會指出差幾個。箱子不能一開始就放在調度口上。

設計調度口的房間時，要確認沒有任何一推會讓箱子永遠卡住。箱子推到牆邊之後，就只能沿著牆推，推進牆角就再也推不動；出房間再進來雖然能讓箱子回到原位，但玩家不一定想得到。序章倉庫（`prologue/warehouse`）的做法是讓輸送帶沿著東、南、北三面牆繞一圈，把箱子送進西北角的調度口：箱子被推到東、南、北牆邊都會上輸送帶，被推到西牆邊則可以沿著西牆往北推進調度口，所以每一推都還有路。地圖檢查看不出這種卡死，要靠試玩確認；序章的倉庫就是在瀏覽器試玩時才發現第一版會卡住而重新設計的。

## 肝臟工廠與急救

肝臟章（設計文件 7.7 節）的化工廠由三個 Line 物件組成，`stage` 各選一種。`receiving` 是收貨區，畫成矩形，蓋住的格子永遠是實心的，像一排櫃檯；`alcohol` 標籤是幾杯，收貨區前幾格就擺幾桶酒精，多於格數的不另外畫。`outlet` 是出貨口，放一個點，第一產線處理完的乙醛箱從這裡附近的空地板出來。`intake` 是第二產線，畫成矩形，乙醛箱停在上面就被收下，`acetaldehyde` 標籤減一。一間房有收貨區，就必須三種各一個，地圖檢查會指出少了哪一種、多了哪一種、畫成點的矩形、整片蓋在牆上的區域，以及放在變體圖層的產線，因為酒精與乙醛記在整章的標籤上，工廠不能隨狀態出現或消失。收貨區上不能放第二產線、調度口、輸送帶、出生點、NPC、道具、床、開關或 Spawn，因為那幾格在遊戲中是實心的，地圖檢查會指出（`dock-blocked`）；觸發區可以跨過收貨區。

第一產線的速度只有一個：每小時處理 `params.json` 的 `liverRate` 杯（目前 0.6），只看章內時鐘，任何道具、工具、標籤或選項都改不了它。章內時鐘往前走的地方（對話與卡片的 `clock:` 效果、`clock_advance` 觸發區、床上等待）都會讓產線跑。一杯完全處理完才變成一個乙醛箱，所以 `alcohol` 從 2 降到 1.4 時收貨區仍是兩桶。酒精桶打不掉：釘書針打到只會彈開並提示「只能等輸送帶」，在旁邊蓋駁回印章也會顯示無效。

乙醛箱是 `boxType` 為 `acetaldehyde` 的推箱，由產線產生，不能畫在地圖上，地圖檢查會擋下。它和其他推箱一樣推、一樣被輸送帶帶走，但周圍兩格內有紅霧：營運長連續待在紅霧裡每 2 秒少半顆心，閃身也躲不掉，走出紅霧就重新計時。乙醛箱不會被調度口收下，進房時也不記得上一趟推到哪裡，每次進房都重新擺在出貨口旁邊。設計工廠房間時，請讓推到牆邊的乙醛箱還有路到第二產線，例如灰盒的 `liver/factory` 讓南牆的輸送帶把箱子送進東南角的第二產線。要等產線清空才能過的門，用 `resource` 鎖寫 `alcohol==0`。

空腹喝酒時（`fasting` 加上 `alcohol>0`，也就是修飾器 `mod.warehouse_locked`），肝醣倉庫暫停出貨：血糖不再補到 45，會一路降到 30 為止，跌破 35 時營運長頭暈冒冷汗，畫面變暗，移速慢 15%，並設定 `dizzy` 標籤，可以拿來當道具或對話的條件。倉庫恢復出貨的那一刻血糖立刻補回 45。

急救流程寫在 `content/rescue.json`，房間裡用 Trigger 開啟，`event` 選 `rescue`、`eventId` 填急救的 id。一段急救有依序要做的 `steps`、錯誤做法 `myths`、面板上列出的順序 `order`（要剛好是 steps 與 myths 的全部），可選的 `helper`（`when` 條件成立時，輪到 `step` 那一步會由別人代勞），以及完成後的 `effects`，寫法和對話的效果相同，以故事事件的身分生效。急救沒有失敗：選到錯誤做法會由朋友說明為什麼不行，選到還沒輪到的步驟會提醒先做哪一步，兩者都不會結束面板，也不會扣血或讓時間前進；做完全部步驟、按確定才關閉。面板上的文字放在字串表：標題 `rescue.<id>.title`、`rescue.<id>.prompt`、每個動作的 `action.<動作>` 與 `reply.<動作>`、`early`（`{step}` 會換成下一步的名稱）、有 helper 時的 `helper`，以及 `done`；所有急救共用的操作說明、進度與繼續提示是 `rescue.hint`、`rescue.progress`、`rescue.continue`。做完全部步驟後，按確定、按數字鍵或用滑鼠點一下面板都會關閉。`npm run check` 會指出缺少的字串、順序不完整、helper 的步驟不在 steps 裡，以及效果寫錯；地圖檢查會指出 `eventId` 不存在的急救觸發區。

## 道具與員工手冊

Pickup 是撿得起來的道具，走到旁邊按 E 或 Enter 撿起，撿起後從房間消失，離開再回來也不會再出現。`itemType` 決定撿起來的效果：

| `itemType` | 撿起來會怎樣 | `itemId` 填什麼 |
| --- | --- | --- |
| `handbook` | 員工手冊解鎖一頁，畫面跳出頁名；已經有的頁會提示「已經在員工手冊裡了」 | 手冊頁代號，必須存在於 `content/handbook.json`，例如 `caffeine` |
| `coffee` | 咖啡因殘留加一杯的量（目前 100），咖啡斗篷下一刻就生效 | 留空，或當鑰匙時填名字 |
| `file` | 沒有其他效果，適合當鑰匙 | 鑰匙名字，對應門的 `lockParam` |
| `memory` | 記憶文件（設計文件 7.4）：章節檔有 `archive` 時，先拿在手上（`archive.held` 標籤加一），要交給暫存桌才算數，睡著時再依 `archive` 換算成準備度；手上滿了就拿不起來，文件留在原地。章節檔沒有 `archive` 時只會消失並跳出提示 | 留空 |
| `meal`、`ors`、`thanks_card` | 目前只會消失並跳出提示；吃飯、電解質液與感謝卡的規則還沒做 | 留空 |

`when` 在進房時判斷一次：不成立時這一趟道具不在房間裡，下次進房再重新判斷。撿起的道具與打卡機的關係和午睡沙發相同：打卡之後才撿的道具，強制下班回到打卡機時會回到原位，因為時鐘與標籤也回到打卡當時，咖啡的殘留也一起還原；打卡之前撿的，回到打卡機後仍然算撿過。手冊頁是例外：解鎖的頁面不會因強制下班而消失，所以手冊頁撿了就不會再出現。

員工手冊的頁面寫在 `content/handbook.json`，依顯示順序排列，每頁有 `id` 與 `body`。頁名放在字串表的 `handbook.<id>.title`，`body` 列出每一段文字的字串代號，例如 `handbook.caffeine.1`，每段各自在字串表填 `fact` 欄，讓查證可以逐句對照。目前只有〈早餐與肝臟〉、〈咖啡因〉、〈睡眠債〉、〈短暫午睡〉四頁，文字取自設計文件的寫法，等內容組依核准句庫補齊與校對。缺頁名或段落文字時，`npm run check` 會指出，遊戲也不會啟動。每一頁都必須在兩種字級下放得進頁面，測試會檢查。

遊戲中按 Tab 打開員工手冊，畫面左邊列出全部頁面，還沒找到的顯示為「？？？」，W／S 翻頁，Tab 或 Esc 關閉；手冊打開時房間暫停，章內時鐘也不走。解鎖的頁面存在瀏覽器裡的跨局進度，不會因為重新開始、讀取打卡點或換章節而消失。對話裡的 `unlock:` 效果與撿起手冊頁的效果相同。灰盒章節的 `greybox/archive` 放了一杯咖啡與儲藏室的鑰匙，`greybox/storeroom` 放了兩頁手冊。

## 把房間接起來

房間本身不知道門通往哪裡。章節的串接寫在 `content/chapters/<章>.json`，檔名與裡面的 `id` 必須和地圖資料夾同名。範例（`content/chapters/greybox.json`）：

```json
{
  "version": 1,
  "id": "greybox",
  "start": "greybox/greybox-room",
  "links": [
    { "a": "greybox/greybox-room#door-s", "b": "greybox/rest-room#door-n" },
    { "a": "greybox/rest-room#door-e", "b": "greybox/brain-corridor#door-w" }
  ]
}
```

`start` 是新遊戲進入的房間。`links` 的每一項把兩扇門接在一起，寫法是「房間路徑#門的名字」，房間路徑是資料夾加檔名、不含 `.tmj`，門的名字就是 Tiled 物件的 Name 欄。兩扇門必須面對面：北門接南門、東門接西門。接好之後從任一邊走過去，都會出現在另一間房的那扇門前。

章節檔還有幾個可以不填的欄位（`carry` 與 `archive` 見下一節），序章 `content/chapters/prologue.json` 全部用上了：

```json
{
  "version": 1,
  "id": "prologue",
  "start": "prologue/lobby",
  "next": "greybox",
  "intro": "prologue.interview",
  "tools": [],
  "glucose": true,
  "links": [ ... ]
}
```

`next` 是這一章結束後接著玩的章節，必須是另一個存在的章節檔，不能是自己；沒填就回到標題畫面。`intro` 是新遊戲進入 `start` 房間時立刻開啟的對話，必須存在於對話 CSV；用 `?room=` 從別的房間開始試玩時不會播。`tools` 列出這一章開場就有的工具，目前有 `stamp`（駁回印章）與 `folder`（公文夾）；寫成 `[]` 表示一開始什麼都沒有，要靠對話的 `grant:` 效果拿到；不填這個欄位則全部工具都有，灰盒章節就是這樣。從上一章接過來的工具會一直保留。`glucose` 設為 `true` 時畫面上方出現血糖表，血糖隨營運長走動慢慢下降，低於 40 時自動補回 45，代表肝臟分解肝醣補上；開場值 55 是暫定的假設，數值寫在 `src/core/chapter/glucose.ts`。

檢查腳本對章節有幾條規定。每扇打得開的門都要接到某個地方；故意留著暫時不用的門，把 `lock` 設成 `key`、`lockParam` 留空即可。同一扇門只能接一次。整章的房間都要從 `start` 走得到：`none`、`clock`、`resource` 的門算通路，`switch` 的門在有拉桿指向它時算通路，`key` 的門在房裡有鑰匙時算通路，`lockParam` 留空的 `key` 門與只靠壓力板開的門不算。`clock` 與 `resource` 的條件實際上會不會達成，檢查腳本看不出來，要靠試玩確認。每間房都要有 PlayerStart。放在 `variant:` 圖層裡的門沒辦法寫進章節檔，所以那種門一定要設成 `lock` 為 `key`、`lockParam` 留空，或把門移到變體圖層之外。新增一個地圖資料夾時，也要在 `content/chapters/` 加上同名的章節檔，漏掉會被檢查指出。`next` 與 `intro` 指到不存在的章節或對話，也會被檢查指出。要讓新章節出現在遊戲裡，還需要程式組把它登記進 `src/app/content.ts` 的 `CHAPTER_FILES`；清單的第一章就是「新遊戲」進入的章節，目前是序章。

序章 `public/assets/maps/prologue/` 是給內容組照抄的範本章節，由 `tools/maps/make-prologue.ts` 產生，五間房依序是大廳（面試、人資發員工證、打卡機、肝與第一頁手冊）、貨運大廳（兩隻飛蟲的戰鬥教學）、倉庫（三個葡萄糖箱、繞牆的輸送帶與調度口）、會議室（董事長發駁回印章、可以試蓋的練習假人、簽了試用合約才開的東門）與夜間辦公桌（凌晨兩點的簽名，然後下班打卡結束這一章）。每一種機制都在裡面出現一次，接法就是在 Tiled 裡應有的接法；台詞是依設計文件起草的版本，內容組可以直接改寫 `content/dialogue/prologue.csv`。

## 章節的歸檔與帶入

章節結束時，這一章的標籤不會帶進下一章，下一章只從章末卡的選擇開始。章節檔的 `carry` 列出要例外帶過去的標籤名稱，這些標籤在章節結束時的值會成為下一章的起點，沒有值的標籤略過。帶過去的標籤只留一筆因果紀錄（來源是 `carry`），這一章打過的卡片不會跟著過去，所以下一章不會把同名的章首卡當成已經回答過。

章節檔的 `archive` 把「記憶文件」換算成準備度，用在設計文件 7.4 與 7.6 的「睡眠有助記憶保存」：

```json
"carry": ["exam_practice", "exam_archived"],
"archive": { "held": "memory_held", "hands": 3, "desk": "memory_desk", "total": 6, "into": "exam_archived" }
```

房間裡 `itemType` 為 `memory` 的 Pickup 每撿一份，`held` 標籤（手上的文件）加一；手上已經有 `hands` 份時撿不起來，文件留在原地，畫面提示手上滿了。手上的文件還不算數，要和暫存桌上的人對話：對話裡寫 `move:memory_held>memory_desk*100`（見「效果」一節），手上每一份在 `desk` 標籤加 100，也就是桌上一份文件是 100。桌上的文件每過一個遊戲小時淡化 5%，這個比例寫在 `content/tags.json` 裡 `desk` 標籤的 `fadePerHour`；手上的文件不淡化，所以要在忘光之前去睡。暫存桌是一個 NPC，大腦章放在海馬迴的西牆邊（`brain.desk`），避開手機精靈與文件，免得對話被搶走。

只有睡著（`bedType` 為 `sleep` 的床）時才設定 `into` 標籤，值是桌上剩下的量佔 `total` 份的百分比，再乘上夜班清潔隊的咖啡因係數：咖啡因殘留低於 15 時為 1，之後隨殘留下降，到 33 約為 0.87（`content/params.json` 的 `cafDeadZone` 與 `cafSleepK`，設計文件 9.1），若章節檔有 `climax` 而且玩家選了多喝一杯，還要再乘上它的 `archiveFactor`。床的 `requires` 決定睡不睡得成，大腦章的就寢門寫 `caffeine<50`，所以殘留 15 到 50 之間門只開一半，清潔隊人手變少。醒著沒睡就換章不會設定 `into`，仍在手上沒交出去的文件也不算。`held`、`desk` 與 `into` 都要是數值標籤，`desk` 標籤還要有 `fadePerHour`，`total` 要等於章節房間裡的記憶文件份數，`hands` 要是不超過 `total` 的正整數，`into` 要列在 `carry` 裡，檢查腳本會逐項指出。

### 章節檔的其他欄位

`climax` 是設計文件 7.4 的「最後一杯」：Boss 戰前由房間裡一張 `once` 的事件卡讓玩家選，選了多喝一杯就設定 `flag` 指定的布林標籤（來源要含 `event`）。寫法是 `"climax": { "flag": "one_more_cup", "summonFactor": 2, "archiveFactor": 0.5 }`：這一章的房間裡，咖啡因 Boss 第二階段每次召喚的腺苷數與同時存在的上限乘上 `summonFactor`，睡著時歸檔量乘上 `archiveFactor`（只能和 `archive` 一起用）。大腦章的事件卡 `climax` 放在海馬迴通往會議室的樓梯前，橫跨整層地板，所以走不到樓梯而不被問到。

`closedCases` 讓一章記住「已經結案」的敵人：`"closedCases": { "energy_seller": "seller_closed" }` 表示能量飲料推銷員被結案時設定 `seller_closed`（布林標籤），而放他的 Spawn 寫 `when` 為 `!seller_closed`，之後每次進房他都不會再出現。敵人檔裡飛行型的敵人可以填 `"throws": "can"`，讓牠丟出的是罐裝能量飲料而不是紙張：罐子要格擋或閃開，打中的人不扣心，而是咖啡因殘留加 150（`content/params.json` 的 `energyDrink`），殘留已超過 300 時推銷員會說出 Disco 那句台詞。

`partner` 指定這一章帶著哪位夥伴，目前只有 `"partner": "chairman"`，按 L 舉起董事長的「畫大餅」護盾：護盾罩住營運長 2.5 格的範圍 4 秒，擋掉範圍內飛來的投射物（不擋範圍攻擊與近戰），然後冷卻 12 秒，冷卻是每進一間房重新計算。範圍與持續時間都乘上 S，S 由睡眠決定，所以睡得少的日子護盾又小又短，畫面上的狀態列會顯示「大餅 ×S」。基本數值寫在 `src/core/combat/pie.ts`，是等試玩調整的暫定值。

這一章的房間靠北門與南門疊成四層樓：教學室、辦公室、海馬迴、會議室與屋頂依序往上，`links` 把下一層的南門接到上一層的北門，大廳、總務處與教學室之間仍然走東西門。

## 在瀏覽器試玩

在專案根目錄執行 `npm install` 與 `npm run dev`，用網址直接進指定的房間：

```
http://localhost:5173/?room=greybox/rest-room&tags=caffeine:50
```

`room` 是房間路徑；`tags` 是進房時身上的狀態標籤，數值標籤寫成 `名稱:數值`、布林標籤只寫名稱，用逗號隔開；`halves=2` 讓營運長只剩 2 個半顆心，方便測試強制下班；`gauge=100` 讓駁回量表直接是滿的。這些參數只在開發版有效，正式版會忽略。房間裡按 F1 可以看到碰撞框。

## 提交前

執行 `npm run check`（只想檢查地圖時執行 `node tools/check-maps.ts`，只檢查資料檔時執行 `node tools/check-content.ts`，只檢查對話時執行 `node tools/check-dialogue.ts`，只檢查卡片時執行 `node tools/check-decks.ts`）。通過時最後一行是 `0 problem(s)`。有問題時每一行是一個問題，開頭是檔名，接著是物件編號與原因，例如：

```
public/assets/maps/brain/coffee-room.tmj 物件 #4（Door）：門「door-e」沒有接到任何房間，卻打得開（lock 為 none）；請在章節檔連起來，或把 lock 設成 key、lockParam 留空
```

合併到 `main` 之前，GitHub 上的檢查會跑同一套規則，沒通過不能合併。

遊戲的字型只收錄內容用得到的字，所以字串或對話用了一個新字時，`npm run check` 會回報「字型子集缺少內容用到的字」。這時執行 `python tools/fonts/build_fonts.py`（需要 Python 3.12 與 `pip install fonttools brotli`，第一次會下載原始字型，約需兩三分鐘），把 `public/assets/fonts/` 裡變動的檔案一起提交即可。重新產生後還是缺的字，代表字型本身沒有這個字，請改用別的字。

## 對話

對話寫在試算表裡，匯出成 UTF-8 的 CSV，放進 `content/dialogue/`，一個檔案可以放很多段對話，同一個 `dialogueId` 不能出現在兩個檔案。第一列是表頭，欄位名稱與順序固定：

| 欄位 | 內容 |
| --- | --- |
| `dialogueId` | 這一段對話的名字，Tiled 的 NPC 與 Trigger 就是用它接上；同一段對話的每一句都填同樣的名字 |
| `order` | 這一句在該段對話裡的順序，從 1 開始的整數，同一段裡不能重複；播放順序看 `order`，不看列在檔案裡的先後 |
| `speaker` | 說話者代號，必須登記在 `content/speakers.json`；玩家的選項一律寫 `operator` |
| `expression` | 表情，對應立繪 `public/assets/portraits/portrait-<說話者>-<表情>.png`；玩家的選項可以留空 |
| `text` | 台詞或選項文字；有逗號或換行時，整格要用雙引號包起來 |
| `condition` | 條件式，語法與 Tiled 的 `when` 相同；不成立時這一句被略過，留空表示一定顯示 |
| `effect` | 這一句出現時（選項則是被選中時）發生的事，多個效果用分號隔開，寫法見下方 |
| `next` | 這一句之後接哪裡：另一列的 `order`，或 `end` 表示結束；留空就接下一列 |
| `fact` | 台詞若含生理說法，填衛教查證表的條目編號；查證尚未完成的填 `pending:編號`；也可以填 `general`，意思與標籤字典和字串表裡的 `general` 相同；沒有生理說法就留空 |

範例（`content/dialogue/greybox.csv` 中腦的簡報）：

```csv
dialogueId,order,speaker,expression,text,condition,effect,next,fact
greybox.brain.briefing,1,brain,normal,早安，營運長。今天的待辦有點多。,,,,
greybox.brain.briefing,2,brain,surprised,你的黑眼圈比昨天深了。,sleep_debt>=2,,,
greybox.brain.briefing,3,brain,normal,先從哪一件開始？,,,,
greybox.brain.briefing,4,operator,,先趕報告。,,tag:deadline;clock:30,7,
greybox.brain.briefing,5,operator,,先去補眠。,,clock:20,8,
greybox.brain.briefing,6,operator,,晚點再說。,,,end,
greybox.brain.briefing,7,brain,warning,好。截止時間逼近了，記得存檔。,,,end,
greybox.brain.briefing,8,brain,sleepy,好。睡醒再說。,,,,
```

### 一段對話怎麼走

對話從第一句開始往下走。說話者的句子顯示在對話框裡，按 E、Enter、J、空白鍵、K 或滑鼠左鍵繼續（互動、攻擊與閃身的按鍵都算確認）。連續 2 到 3 列 `speaker` 為 `operator` 的列是一組玩家選項，會以便利貼從畫面右側滑出；用 W、S 移動、再按確認鍵，或直接按 1、2、3，也可以用滑鼠點選項（選項出現時，滑鼠只有點中便利貼才算數，點在空白處不會送出目前選中的選項）。選了之後接著走那個選項自己的 `next`，沒填就接在這一組選項後面的第一列。`next` 只能指向比自己大的 `order`，所以每一段對話一定會結束；它也不能指向一組選項的中間。上面的範例裡，第 4 列選了之後接第 7 列，第 5 列接第 8 列，第 6 列直接結束，所以第 7 列要自己寫 `end`，否則會接著念第 8 列。

條件讀的是當下的標籤。說話者的句子條件不成立就略過，接著看下一列；選項條件不成立就不出現；一組選項全部不成立，整組略過；整段都被略過時，對話不會開啟。選項生效之後的下一句，看得到那個選項剛設定的標籤。

### 效果

`effect` 可以寫好幾種，用分號隔開，依序生效：`tag:名稱` 把布林標籤設為成立；`tag:名稱=數字` 把數值標籤設為該值；`tag:名稱+數字` 把數值標籤加上該值；`move:甲>乙*倍數` 把數值標籤甲清空，每一單位在乙加上倍數，例如 `move:memory_held>memory_desk*100` 把手上的文件放到暫存桌上，甲與乙都要是數值標籤、彼此不同、對話可以設定，也不能是酒精、咖啡因、血糖或睡眠債；`clock:分鐘` 讓章內時鐘前進，說話是花時間的；`unlock:手冊頁代號` 解鎖一頁員工手冊；`grant:工具` 交給營運長一項工具，目前有 `grant:stamp` 與 `grant:folder`；拿到印章時駁回量表直接填滿，可以馬上試蓋，拿到公文夾時只是放進口袋，玩家按 F 才會換上。`grant:` 只能寫在對話與事件卡，章首卡與章末卡不能用。對話只能改標籤字典裡來源含 `event` 或 `chapter` 的標籤，來源只有 `card` 或 `rule` 的標籤（例如早餐）由卡片或規則算出來，對話不能直接設定。咖啡因的來源含 `chapter`，因為房間裡的咖啡道具會加它，所以對話也可以寫 `tag:caffeine+100`，例如推銷員遞上一杯咖啡。名稱以 `mod.` 開頭的修飾器是由標籤條件算出來的，同樣不能設定，要改它所依據的標籤。每個標籤的變動都會記進因果紀錄，寫明是哪一段對話的哪一句造成的。喝酒永遠不是戰鬥增益（設計文件 5.1）：任何效果都不能寫 `tag:alcohol=數字`，酒精只能由肝臟產線處理掉；加酒精的那一格效果，也不能同時發工具、設定睡眠債，或增加咖啡因與血糖。對話、卡片與急救的檢查都會擋下這兩種寫法。

### 說話者與兩種版面

`content/speakers.json` 登記每個說話者的 `style` 與 `portrait`。每個說話者還要在 `content/strings/zh-TW.json` 有一則 `speaker.<代號>` 的名牌文字，少了的話 `node tools/check-content.ts` 會報錯。`operator` 是玩家選項專用的代號，不能登記。

`style` 為 `box` 的說話者使用畫面下方的對話框，左上角有名牌，立繪站在對話框左上方，下緣被框蓋住一截。`style` 為 `memo` 的說話者用在肝，肝不說話，沒有對話框，台詞寫在畫面中央偏右的一張便利貼上，立繪站在畫面左下。立繪每次只顯示正在說話的那一位；玩家選項出現時，對話框裡仍是上一句說話者的台詞。`portrait` 為 `false` 的說話者不需要立繪檔。

### 長度限制

對話框每行最多 30 個全形字、最多 3 行。玩家選項的便利貼最多 2 行，100% 字級每行 17 字，125% 字級每行 14 字，所以 28 字以內在兩檔字級都放得下。肝的便利貼最多 3 行，100% 字級每行 13 字，125% 字級每行 10 字，所以 30 字以內都放得下。斷行規則和遊戲相同，例如收尾標點不落在行首，所以標點多的句子可能比字數看起來更早換行。兩種便利貼的寬度是暫定值，美術確認前可能調整。

### 宿主的名字

宿主（公司營運的那位學生）的名字由玩家在新遊戲開始前決定，預設是「小晨」，之後也可以在標題畫面更改。所以內容裡不要直接寫「小晨」，要寫 `{host}`，遊戲畫出文字時會換成玩家取的名字，例如：

```csv
prologue.brain.wake,1,brain,normal,{host}又熬夜了。,,,,
```

`{host}` 可以用在對話 CSV 的 `text` 欄，以及 `content/strings/zh-TW.json` 裡卡片、手冊、HUD 與便利貼的文字，一句裡寫幾次都可以。

- **長度**：名字最多 6 個字。對話、卡片與手冊的長度檢查一律把 `{host}` 當成 6 個全形字來量，所以用「小晨」放得下、換成 6 個字就超出的句子會被擋下，請預留空間。
- **報告不能用**：結算報告依設計文件第 3 節一律稱「宿主」、寫給營運長，所以 `report.` 開頭的字串不能寫 `{host}`，`npm run check` 會擋下。
- **拼錯會被抓到**：`npm run check` 會檢查字串表與對話裡所有 `{...}` 佔位符，不認得的（例如打錯成 `{hots}`）會報錯，不會直接顯示給玩家。程式新增其他佔位符時，要登記在 `tools/check-content.ts` 的 `PLACEHOLDERS`。

### 檢查

`node tools/check-dialogue.ts`（`npm run check` 已包含）用遊戲讀檔的同一支程式讀 CSV，所以它放行的檔案遊戲一定讀得進去。它檢查表頭與欄位數、`order`、條件式與效果的寫法、`next` 的目標存在且只往後、每組選項是 2 到 3 列、每一句都有辦法走到、說話者已登記、立繪檔存在、文字放得進版面，以及 `unlock:` 指到的手冊頁存在。有任何一列出問題，整段對話都不會載入，遊戲啟動時也會直接停下並列出問題，所以不會有只剩一半的對話；欄位數不對的那一列也一樣，整段對話會被整個略過，不會再連帶報出一串「找不到下一句」。訊息裡的列號和試算表顯示的一致，空白列也算一列。地圖檢查確認 Tiled 裡寫的 `dialogueId` 存在於某個 CSV，遊戲啟動時也會對每張房間地圖再確認一次，所以舊的打包檔不會等到玩到一半才出錯。

`npm run check:release` 多擋一項：`fact` 還是 `pending:編號` 的句子，表示衛教查證還沒完成，不能發行。目前沒有任何工作流程會自動執行它，發行前要手動跑一次。字串表 `content/strings` 裡的 `pending` 標記不在這個檢查的範圍內。

### 目前還沒有的

台詞整句直接顯示，沒有逐字出現的效果。同一個 tick 只會開一段對話；同時踩到兩個對話觸發點時，後一個被丟掉；如果它是只觸發一次的觸發點，會還回來，離開再踩進去就能觸發。同理，整段都被條件略過、沒有開起來的對話，也不會用掉它的觸發點。每一句出現後的前 12 個 tick（0.2 秒）按鍵不算，避免戰鬥中按住的鍵把第一句直接跳過，這個時間是暫定值，要看試玩的感覺再調。

## 卡片

每一章的外層卡片寫在 `content/decks/<章>.json`，檔名與裡面的 `chapter` 都要和章節檔同名。卡片主要分兩種（另有章末卡，見本節後段）：章首卡在新遊戲進入第一間房之前依序翻開，決定這一章開局有多糟（例如昨晚幾點睡、早上有沒有喝咖啡）；事件卡在章節中途由 Tiled 的 Trigger 翻開，`event` 選 `card`、`eventId` 填事件卡的 id。範例（`content/decks/greybox.json` 的一部分）：

```json
{
  "version": 1,
  "chapter": "greybox",
  "opening": [
    {
      "id": "morning_coffee",
      "options": [
        { "id": "drink", "effect": "tag:caffeine=100" },
        { "id": "skip", "effect": "" }
      ]
    }
  ],
  "events": [
    {
      "id": "group_chat",
      "options": [
        { "id": "rewrite", "effect": "tag:deadline;clock:60" },
        { "id": "office_hour", "effect": "tag:stress+10" }
      ]
    }
  ]
}
```

章首卡最多 3 張，每張卡有 2 到 3 個選項。卡片 id 在整個卡組裡不能重複（章首卡與事件卡共用一套 id，因為卡面文字以 id 為鍵），同一張卡的選項 id 也不能重複。`effect` 的寫法與對話相同，留空表示這個選項不改變任何狀態，但選擇本身仍會記進因果紀錄，結算報告才知道玩家選了什麼。章首卡只能設定標籤字典裡來源含 `card` 的標籤，事件卡只能設定來源含 `event` 的標籤。

卡面文字放在 `content/strings/zh-TW.json`：題目是 `deck.<章>.<卡>.title`，每個選項的名稱是 `deck.<章>.<卡>.<選項>`，名稱下方的說明是 `deck.<章>.<卡>.<選項>.note`。題目最多 2 行，選項名稱最多 2 行，說明最多 4 行，在 100% 與 125% 字級都要放得下。選項說明是玩家做決定時唯一的線索，請寫出這個選擇在章節裡會造成的結果，例如「睡眠債 2 小時：走廊多兩個腺苷通風口」。

章首卡畫面可以用 W、S、A、D 或方向鍵移動，按 E、Enter、J 或空白鍵確定，也可以直接按 1、2、3 或用滑鼠點卡片。事件卡出現時房間與章內時鐘都會停住，用 W、S 移動、確認鍵確定、1 2 3 直接選，或點卡片；點在卡片以外的地方不算數。和對話一樣，卡片出現後的前 12 個 tick 按鍵不算。帶有事件卡的 Trigger 預設只觸發一次。

章內時鐘在探索時會自己走，現實 55 秒是遊戲裡 1 小時（`content/params.json` 的 `exploreSecondsPerHour`）；對話與事件卡打開時時鐘停住。咖啡因殘留隨時鐘以 5 小時半衰期遞減（`halfLife`），殘留 50 以上時腺苷完全看不到營運長，不會飄過來也不會黏上，25 到 50 之間只在 2 格內察覺，25 以下恢復正常。

卡組還可以有第三種卡：章末卡寫在 `closing`，最多 3 張，寫法與章首卡相同，也只能設定來源含 `card` 的標籤。章節結束時（睡覺或 `end` 觸發點），章末卡在標題「下班之後」下依序翻開，選擇的效果帶進 `next` 那一章的開場。序章用它問「今晚幾點睡？」，答案就是灰盒章節的睡眠債。下一章的章首卡裡，已經在上一章章末回答過的同一張卡（卡片 id 相同）會被略過，所以灰盒章節接在序章後面時只問咖啡，沒有經過序章、直接進灰盒時兩張都問。章節一結束、章末卡翻開之前就會存檔，章末卡回答完再存一次，這時按標題畫面的「繼續」會從下一章的章首卡開始。章末卡還沒回答就關掉遊戲時，「繼續」同樣進下一章，不會回到剛結束那一章的打卡點；沒回答的章末卡如果也在下一章的章首卡裡，會在那裡再問一次。最後一章結束時則清空存檔。

`node tools/check-decks.ts`（`npm run check` 已包含）用遊戲讀檔的同一支程式讀卡組，檢查格式、id、效果寫法、卡面文字是否存在與放得下，並把每一種章首卡組合實際帶進章節：每間房都要進得去，而且在等待 24 小時之內，至少有一張 `bedType` 為 `sleep` 的床的 `requires` 會成立；每一張事件卡的每個選項也會疊在每種組合上再試一次。任何一種組合讓章節無法結束，檢查就失敗。檢查同時列出每種組合的敵人數、董事長精神 P 與「壓力」，以及最難組合比最簡單組合難多少，設計文件的目標約 30%；這個數字只記錄、不會讓檢查失敗。壓力是敵人數除以 P，其中會黏人的敵人（腺苷）按咖啡因斗篷打折：從開場到 23:00 的每一分鐘，看它當下的偵測距離佔正常距離的比例（看不見算 0，只在 2 格內察覺算 2/5），取平均。早上一杯咖啡讓腺苷在這一天平均只看得見約 47%。檢查也列出每個選項的影響，也就是含有該選項的組合平均壓力，用來找出是哪一張卡拉開差距。壓力還沒有計入 P 對幹勁上限的影響，因為規則還沒做。地圖檢查確認 Trigger 寫的事件卡存在於該地圖資料夾那一章的卡組，遊戲啟動時也會再確認一次。

## 尚未驗證的事

Tiled 在「另存新檔」時是否會改寫範本裡圖塊集的相對路徑，目前沒有在 Tiled 裡實際確認。範本與正式房間在同一層資料夾，直接複製檔案不會有路徑問題；若在 Tiled 裡另存新檔後圖塊消失，請改用檔案總管複製範本。
